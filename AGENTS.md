# AGENTS.md

Plataforma WhatsApp multi-bot: `gateway/` (Node.js + Baileys) + `brain/` (Python FastAPI). CI en GitHub Actions (lint + tests por componente); ver secciones abajo.

## Arranque (orden importa)

1. Brain primero: `cd brain; python main.py` (venv: `venv/bin/python` Linux / `venv\Scripts\python.exe` Windows) → FastAPI en `127.0.0.1:5100` (env `BRAIN_PORT=5100`, bind `BRAIN_HOST=0.0.0.0`; rango DEV backend 5100-5199, ver `playground/PORT_ALLOCATION.sdk-bot.md`). El gateway lo alcanza vía `BRAIN_API_BASE=http://127.0.0.1:5100` (config.js ya lee esta env, fallback :8000 legacy).
2. Gateway: `cd gateway; npm start` (o `node index.js`). El panel web opcional va en `ADMIN_WEB_PORT=5201` (bridge 5200-5299) y el status server en `STATUS_PORT=5300` (misc 5300-5399), ambos bind `0.0.0.0` para acceso por Tailscale.
3. QR nuevo / re-sincronizar libreta: `cd gateway; npm run reset` (borra `auth_info_baileys/` tras confirmar y lanza index.js). **Reset limpio (fábrica, F7): `cd gateway; npm run clean`** — para + brain si corren, borra TODO el estado de runtime (sesión, agenda, settings, broadcasts, cola, memory.db, logs, locks) y relanza; la app queda como recién clonada (los perfiles SOUL se conservan). Doble confirmación.
4. **Producción (F1):** despliegue unificado por plataforma en `deploy/` (`linux/` systemd --user, `termux/` runit, `windows/` scripts). Linux: `bash deploy/linux/install.sh` (systemd --user, sin sudo); Termux: `bash deploy/termux/setup-termux.sh`; Windows: `deploy/windows/startBrain.bat` + `startGateway.bat`. Verificar con `systemctl --user status sdk-bot-{brain,gateway}` y `journalctl --user -u sdk-bot-gateway -f`.

**Desarrollo vs producción:** nunca corras manual y systemd del mismo componente a la vez (el lock de instancia única bloquea al segundo). Usa `bash deploy/linux/dev.sh`:
- `dev.sh manual brain|gateway|ambos` — detiene el service systemd --user y lanza la instancia manual (foreground, Ctrl+C al terminar; `ambos` imprime los comandos para 2 terminales).
- `dev.sh reset brain|gateway|ambos` — mata las instancias manuales y relanza los services de systemd --user.
- `dev.sh status` — estado de services y locks.

Logs: `gateway/logs/gateway.log` y `brain/logs/brain.log` (rotación 5MB, 3 backups). Ver en vivo: `tail -f gateway/logs/gateway.log | pino-pretty` (instalar pino-pretty aparte) o `cat` directo (JSON por línea).

Setup primera vez (Linux Debian/Ubuntu): `sudo apt install python3-venv` → `cd brain; python3 -m venv venv && venv/bin/pip install -r requirements.txt`. Windows: `python -m venv venv && venv\Scripts\pip install -r requirements.txt`.

## Arquitectura

- `gateway/index.js` — entrada Baileys (`syncFullHistory: true`, `presenceSubscribe`, `markOnlineOnConnect`). El admin se detecta solo (`state.ADMIN_PHONE/LID`). Reconexión con **backoff exponencial 2s→5s→15s→60s** (reset en `open`); socket anterior se cierra con `sock.end()` antes de recrear. La agenda entrante se encola en `contactSyncQueue` (chunks de 300/tick); `messaging-history.status` loguea el progreso de la sync inicial.
- `gateway/config.js` — `state` global (`CURRENT_PROFILE`, `GLOBAL_MODE`, `IS_BOT_PAUSED`) + registro anti-bucle `botSentMessageIds` (expira a los 60s).
- `gateway/services/db.js` — persistencia `contacts_db.json` (write atómico tmp+rename) + `settings_db.json` con debounce 2s y flush en SIGINT/SIGTERM. Caché en memoria + suscriptores de cambio de caché (`onContactsCacheUpdate`).
- `gateway/services/contactsRepository.js` — lógica de dominio de contactos: `contactStore`, `isJunkJid`, `cleanContactsDB`, `upsertContactMetadata`, `bulkUpsertContactsMetadata`, búsqueda `findExistingKey()` O(1) y `findKeyByDigits()`. **Índices RAM** `phoneIndex`/`lidIndex`/`digitsIndex` (R1) con **mantenimiento INCREMENTAL O(1)** (los upserts los actualizan; `cleanContactsDB` los invalida y se reconstruyen en la próxima búsqueda). **`cleanContactsDB()` NO se corre por upsert/lote** (era O(N)+O(N²) por llamada y saturaba el event loop en la sync inicial): solo en el arranque (`index.js`) y bajo demanda (`/sync`).
- `gateway/services/contactSyncQueue.js` — cola de la sync de la agenda (R4): procesa los contactos entrantes (`contacts.upsert`/`contacts.update`/`messaging-history.set`) en **chunks de 300 por tick (`setImmediate`)** para no saturar el event loop durante la sync inicial al vincular (miles de contactos en ráfaga → el socket perdía pings → WhatsApp cortaba la conexión a mitad de la agenda; y esa sync completa SOLO ocurre al vincular, no hay re-sync). `setProcessor`/`push`/`pendingCount`; `resetForTests()` para tests.
- `gateway/services/stateService.js` — `setNumberState` (`*`/individual), `setCurrentProfile`, `setContactProfile`, `ignoreAllAgendaContacts`. Reusa `findKeyByDigits` (sin duplicar scans).
- `gateway/services/metadataService.js` — país/idioma por prefijo (América + Europa), TTL 24h foto/bio, resuelve Phone y LID dual.
- `gateway/services/brainService.js` — cliente REST del brain (timeout global 90s) + simulación humana (typing 7-10 char/s, multi-bubble ~220 chars). **Retry 1x** en errores transitorios (red/timeout/5xx); los 4xx no se reintentan.
- `gateway/services/aiQueue.js` — pool de concurrencia global (máx 3 `processAIChat` en paralelo, cola FIFO). Evita saturar a los proveedores con varios clientes a la vez.
- `gateway/services/messageQueue.js` — cola persistente de mensajes (F4-P4): si el brain falla con error transitorio, el mensaje del cliente se encola en `gateway/queue/pending_messages.jsonl` (JSONL, límite 50 items con env `SDK_MESSAGE_QUEUE_MAX`, TTL 24h, persistencia atómica tmp+rename). El flush lo programa un brain call exitoso (debounce 3s) o un timer cada 30s en `index.js`, y lo ejecuta `messageHandler.js` (`flushQueuedMessages`): FIFO, respetando `chatInFlight`, máx 5 intentos por mensaje. El socket lo setea `index.js` (`setSock`). Los tests la aíslan con `tests/helpers/tmpQueue.js` (`SDK_MESSAGE_QUEUE_PATH`).
- `gateway/services/broadcastService.js` — broadcasts y mensajes programados (F4-P5): `/broadcast <texto>` y `/programar <HH:MM> <texto>` con confirmación en 2 pasos (responde "si"/"cancelar"; interceptada en `messageHandler.js` antes de la IA). Worker de 1 mensaje por tick (10s en `index.js`, solo con conexión abierta), límite diario por contacto (`SDK_BROADCAST_DAILY_LIMIT`, default 2), persistencia atómica en `gateway/broadcast_db.json` (`SDK_BROADCAST_DB_PATH`) con cursor resume-safe (un crash nunca re-envía). Contactos aptos = agenda (`isContact`) sin estado `ignorado`/`handoff`. **Kill-switch (F4-P6): apagados por defecto, incluso en el deploy (el unit systemd NO setea `SDK_BROADCAST_ENABLED`); `isEnabled()`/`setEnabled()`, toggle `/broadcast on|off`, arranque con `SDK_BROADCAST_ENABLED=1` solo si se quiere activo desde el inicio; al apagar se cancelan los pendientes/en curso.** Comandos en `handlers/commands/broadcast.js`.
- `gateway/services/logger.js` — pino + pino-roll (rotación 5MB × 3): `logs/gateway.log` + stdout. Categorías vía `cat('AI'|'DEBOUNCE'|'PRESENCIA'|'COMANDO'|'ERROR'|'CORE'|'INSTANCIA'|'STORAGE')`.
- `brain/logging_setup.py` — logging rotado del brain (RotatingFileHandler a `brain/logs/brain.log` + consola); `safe_log` en providers y logs de main.py/profiles.py lo usan.
- `gateway/services/pipeline.js` — **lógica de decisión de mensajes PURA (F3-P3)**: `decideMessageFlow()` devuelve la acción a tomar (`admin_command` / `self_chat_ai` / `handoff` / `respond` / `ignore` con `reason`) sin side effects (testeable con socket falso). También: `getAdaptiveDebounceMs` (rng inyectable), `checkHumanRequest`, `getCandidateIdsForPresence`, `extractTextMessage`. **Al añadir/editar reglas de flujo, tocar AQUÍ, no en messageHandler.**
- `gateway/handlers/messageHandler.js` — orquestador fino del pipeline: de-bounce (timers/buffers), presencia/typing, serialización por chat (`chatInFlight`), limpieza RAM. Ejecuta la acción que decide el pipeline (envía, agenda, notifica handoff).
- `gateway/handlers/commandHandler.js` — dispatcher de comandos admin del self-chat: rate limit 20/min, extracción de teléfono/LID de citas, tabla de registro `commandRegistry` (alias → handler), envío por chunks. Citar un mensaje extrae teléfono/LID automáticamente.
- `gateway/handlers/commandHelpers.js` — helpers compartidos: `sanitizeMarkdown`, `parsePhoneOrLid`, `isValidTargetId`, `COMMAND_USAGE` + `usageOf`/`syntaxError`, `chunkAdminText`, `extractPhoneFromQuoted`.
- `gateway/handlers/commands/` — módulos por categoría que exportan `[{ aliases: [...], run(ctx) }]` (ctx = `{sock, remoteJid, queryParam, rawMsg}`): `chatControl.js` (/ia /humano /limpiar), `lists.js` (/ignorar /permitir /quitar /listas), `contacts.js` (/buscar /nombre /contactos /sync /export), `system.js` (/pausar /reanudar /info /estado /init), `profiles.js` (/perfil /update + `handleProfileUpload`), `broadcast.js` (/broadcast on|off /broadcast /programar + cancelar/estado). **Comando nuevo = un `run` + entry en la tabla del módulo + importarlo en `commandHandler.js`** (sin tocar el switch gigante).
- `brain/memory.py` — memoria de conversación persistente (F4-P1/P2): SQLite con `append_exchange` (incremental) y `get_history` (ventana temporal de 7 días, sin tope de cantidad, truncado por tokens ~5000 vía chars/4, `WINDOW_SECONDS`/`MAX_MESSAGES`/`MAX_TOKENS` tunables desde `.env.tuning`). `clear_history` por `bot_id`+`user_id`. Para la precarga en presencia (Opción A) `get_history` acepta `max_messages`/`max_tokens` opcionales que acotan el resultado a una "primera página" web-like (etapa 1) sin afectar la respuesta (etapa 2).
- `brain/main.py` — endpoints `POST /chat`, `POST /reset-memory`, `GET /profiles`, `GET /profiles/{key}` (prompt compilado), `GET /profiles/{key}/file`, `POST /profiles/import`, `POST /profiles/reload`, `GET /history` (solo lectura, sin API key: contexto de un chat para la precarga en presencia, acepta `max_messages`/`max_tokens`) y `GET /health` (métricas sin API key: uptime, proveedores, rate-limit, stats de la DB de memoria). **2 etapas de contexto:** (1) precarga en presencia = señal de intervención web-like, ventana reciente acotada (25 mensajes por defecto, `GATEWAY_PRELOAD_*` en `.env.tuning`); (2) respuesta `/chat` = contexto COMPLETO vía `get_history()` (7d / 5000 tok). La precarga NO se inyecta en `/chat`.
- `gateway/services/statusServer.js` — métricas locales (F4-P3): HTTP en `127.0.0.1:5300` (env `STATUS_PORT`, default 5300; rango DEV misc 5300-5399, bind `0.0.0.0` para Tailscale), rutas `GET /status` (estado de conexión, bot, contactos, contadores, buffers/presencias/inFlight, pool de IA, rate-limiter, memoria) y `GET /health`. Para la futura dashboard; nunca exponer a Internet (solo tailnet). EADDRINUSE se loguea y sigue el gateway (no bloquea).
- `gateway/services/adminWebServer.js` — panel web OPCIONAL (F6-P1): se monta solo con `SDK_ADMIN_WEB_ENABLED=1` (hook de 2 líneas en `index.js`); el motor no lo conoce. Consume `commandHandler` con sock virtual (`POST /api/command` → la respuesta va al HTTP; documentos como base64 descargable), `buildStatus` (`GET /api/status`), `GET /api/logs` (SSE de logs en vivo, F6-P3: tail de `gateway/logs/gateway.*.log` y `brain/logs/brain.*.log` con seguimiento de rotación/truncación por tamaño+mtime, filtro por `?component=` y `?history=`) y sirve el front estático `gateway/admin-web/index.html` (HTML+JS puro con pestañas navegables por hash `#dashboard`/`#pairing`/`#contactos`/`#perfiles`/`#logs`: Dashboard = tarjetas con polling 10s + terminal de comandos; Contactos = scroll infinito + búsqueda en vivo con debounce 300ms y ✕; Perfiles = editor de `.md` del brain vía proxy; los SSE de QR y logs y la carga de contactos son perezosos — solo se conectan al abrir su pestaña; la pestaña Logs se reconecta y refresca el historial al volver a ella salvo que esté en pausa). Perfiles SOUL (F6-P5): `GET /api/profiles` (lista), `GET /api/profiles/<key>` (detalle + prompt compilado), `GET /api/profiles/<key>/file` (el `.md` crudo), `POST /api/profiles/import` `{key, content}` (crea/actualiza; el brain valida y normaliza sus `HTTPException {detail}` a `{success:false,message}`), `POST /api/profiles/reload` y `DELETE /api/profiles/<key>` (default protegido) — proxy puro de `brainService` (misma API key). Front: selector desplegable con la lista, editor Markdown, importar `.md` (la clave la define el nombre del archivo), exportar, ver prompt compilado y eliminar. Agenda (F6-P2): `GET /api/contacts` (q/estado/paginación), `GET /api/contacts/<key>`, `POST /api/contacts/<key>/estado` y `/perfil` — consumen `contactsRepository`/`stateService`. Conexión y pairing (F6-P4): el motor solo hace `adminWeb?.setSock(sock)` y `adminWeb?.handleConnectionUpdate(update)`; `GET /api/qr` es SSE que difunde el QR de Baileys renderizado a PNG data URL con `qrcode` (node-qrcode, dependencia) + el campo `session` (hay sesión activa = `ws` de Baileys OPEN; rc14 el ws es un WebSocketClient con getters `isOpen()/isClosed()`, `wsReadyState()` soporta ambos APIs) — el front muestra pairing solo sin sesión y reset solo con sesión, con dos métodos de vinculación al elegir ("Pair con QR" → ventana de 1 min con "Generar QR"; "Pair con número" → código de 8 dígitos), `POST /api/pairing` `{phone}` → `sock.requestPairingCode` (código de 8 dígitos; sin socket activo — o con socket cerrado (`wsReadyState()===3`), p.ej. tras el anti-loop sin sesión — devuelve `needsRestart:true` y lanza el gateway), `POST /api/restart` `{confirm:true}` (lanzar gateway sin borrar sesión), `POST /api/reset` `{confirm:true}` borra `auth_info_baileys/` (env `SDK_AUTH_DIR` para tests) y reinicia (systemctl si `SYSTEMD_EXEC_PID`, exit(0) si no; `SDK_RESET_NO_EXIT=1` solo tests, `resetInProgressForTests()` exportado para tests). **Reset limpio (F7): `POST /api/reset` con `{confirm:true, clean:true}`** borra TODO el estado de runtime vía `factoryReset.js` (ver abajo) y reinicia; con systemd además reinicia el brain (`systemctl restart sdk-bot-brain`, env `SDK_BRAIN_SERVICE`) para que suelte el `memory.db` borrado; en manual avisa que hay que reiniciar el brain. Front: botón "🧨 Reset limpio (fábrica)" con doble confirmación (confirm + escribir `BORRAR`). **Ventana de QR (1 min, siempre manual):** cada intento (arranque sin sesión o pairing) abre una ventana de 60s (`QR_TTL_MS`); los SSE de `/api/qr` llevan `{qr, expiresAt, expired}` y el front muestra countdown regresivo con el botón de pairing BLOQUEADO mientras haya QR vigente; al expirar, el servidor emite `{qr:null, expired:true}`, los QRs regenerados de Baileys se IGNORAN (`qrWindowOpen`) y solo un pairing nuevo (manual) la reabre. Pairing sin teléfono = abrir la ventana del QR (sin `requestPairingCode`). Helpers de tests exportados: `setQrTtlForTests(ms)` y `resetQrForTests()`. Puerto `ADMIN_WEB_PORT` (default 3200, el deploy/systemd usa 3201 porque 3200 lo ocupa el sse-bridge en la máquina del admin), solo 127.0.0.1.
- `gateway/services/factoryReset.js` — **reset limpio (F7): punto ÚNICO de borrado del estado de runtime** para dejar la app "como recién clonada". `getStatePaths()` es el inventario canónico: `auth_info_baileys/` (`SDK_AUTH_DIR`), `contacts_db.json`/`settings_db.json` (de `config.js`), `broadcast_db.json` (`SDK_BROADCAST_DB_PATH`), `pending_messages.jsonl` (`SDK_MESSAGE_QUEUE_PATH`), `brain/memory.db` (`BRAIN_MEMORY_DB`), `logs/` de gateway y brain (`SDK_ADMIN_WEB_LOG_GATEWAY`/`SDK_ADMIN_WEB_LOG_BRAIN`, las mismas envs del panel) y locks (`.gateway.lock`/`.brain.lock` con envs propias `SDK_GATEWAY_LOCK_PATH`/`SDK_BRAIN_LOCK_PATH` por seguridad de tests). `performFactoryReset()` borra y devuelve `{deleted, missing, errors}` (aborta si algo falla: nunca reiniciar a medias). Los perfiles SOUL NO se tocan (versionados en git). **Flag `wiping` (`setWiping`/`isWiping`):** mientras un reset limpio está en curso, `db.js` (debounce + `flushToDisk`) e `index.js` (cierre seguro) NO vuelcan la caché RAM a disco — un flush tras el wipe RESSUSITARÍA las DBs recién borradas. **Helpers de reinicio compartidos:** `restartGatewayProcess()` (systemctl si `SYSTEMD_EXEC_PID` con fallback exit(0); `SDK_RESET_NO_EXIT=1` solo tests) y `restartBrainIfSystemd()` (reinicia el service del brain para que suelte el `memory.db` borrado; devuelve si se disparó). Consumidores: `reset-clean.js` (CLI `npm run clean` — detiene gateway+brain vía locks si corren [SIGTERM→SIGKILL, detecta systemd por `/proc/<pid>/cgroup` para no relanzar a mano], doble confirmación [y/N + escribir `BORRAR-TODO`], borra y relanza lo que estaba corriendo), el panel (`clean:true`) y el self-chat (`/reset-clean`).
- `gateway/services/resetCleanFlow.js` — **confirmación del reset limpio desde el self-chat (F7)**: `requestCleanReset(sock, jid)` devuelve el aviso (lo envía el dispatcher de comandos en chunks) y deja el pedido pendiente; `tryCleanConfirm(text, sock, jid)` se intercepta en `messageHandler.js` en el caso `self_chat_ai` (mismo patrón que la confirmación de broadcast, ANTES de la IA). **Doble confirmación + timers:** la palabra mágica `BORRAR-TODO` (misma en web, CLI y self-chat) NO se acepta antes del timer de LECTURA (`SDK_RESET_CLEAN_READ_MS`, default 10s) y DEBE llegar dentro del timer de ESCRITURA (`SDK_RESET_CLEAN_TTL_MS`, default 60s); al vencer, avisa y cancela solo; "cancelar"/"no" cancela; cualquier otro texto va a la IA y el pedido sigue vigente; un segundo `/reset-clean` con pedido vigente avisa sin duplicar. Al confirmar: `performFactoryReset` + `restartBrainIfSystemd` + `restartGatewayProcess`. `resetForTests()` limpia estado (módulo compartido). Comando en `system.js` (`/reset-clean`, alias `/fclean`, sin argumentos → `syntaxError`), help en `COMMAND_USAGE`, línea en el menú `/e`.
- `brain/providers.py` — cascada real: **Groq → OpenRouter → Gemini** (25s/25s/40s, 90s total). README/PLAN dicen OpenRouter primero; están desactualizados. `google-genai` se importa de forma DEFENSIVA (`try/except ImportError`): en Termux no hay wheel y no se instala; Gemini queda desactivado sin romper el brain.
- `brain/config.py` — `GROQ_MODEL = llama-3.3-70b-versatile`, `OPENROUTER_MODEL = openrouter/free`; Gemini `gemini-flash-lite-latest` hardcodeado en providers.py.
- `brain/profiles.py` — perfiles SOUL en `brain/profiles/*.md` (`default`, `lucia`, `mateo`, `cobranzas`, `recepcion`), parseo Markdown (`# nombre`, descripción, `## Personalidad`, `## Reglas` con viñetas, `## Formato`, `## Ejemplos` en pares `**Cliente:**`/`**Asistente:**`), cache por mtime (recarga en caliente al editar). `build_system_prompt()` cae a `default` si el key no existe.
- Perfil por contacto: campo `perfil` en `contacts_db.json` (opcional). El brain recibe `metadata.perfil || state.CURRENT_PROFILE`; el global se persiste en `settings_db.json` (`currentProfile`) y recarga a `state` al arrancar.

## Editar perfiles desde WhatsApp (self-chat)

- `/perfil exportar <key>` envía el `.md` como documento; editar y reenviar citándolo con `/update` (o caption `/update`) lo importa y actualiza el archivo. Solo se aceptan archivos `*.md`/`*.txt` nombrados `<key>.md` (el nombre del archivo DEFINE la clave del perfil; cualquier `<key>.md` nuevo crea un perfil nuevo).
- `/perfil eliminar <key>` (alias: borrar/delete/del/rm) borra el `.md` vía `DELETE /profiles/{key}`. `default` está protegido. Al borrar un perfil asignado a contactos, el brain cae a `default`.
- `/perfil <key>` (global) | `/perfil <key> <num>` o citando (por contacto) | `/perfil ver <key>` (prompt compilado).
- `/perfil` valida contra `GET /profiles` (brain encendido); con brain apagado lista vacía y rechaza cambios.

## Gotchas

- **Instancia única:** brain y gateway escriben un lock con PID (`.brain.lock`, `.gateway.lock`, gitignored). Abrir una segunda instancia se bloquea con mensaje claro (protege `auth_info_baileys` de corrupción por doble gateway). Para reiniciar: `python main.py --restart` / `npm start -- --restart`. Los locks huérfanos se auto-limpian.
- El brain debe estar corriendo o el gateway envía alerta al self-chat (nunca al cliente).
- **Memoria del brain es PERSISTENTE (F4-P1):** SQLite en `brain/memory.db` (gitignored, se crea al primer uso). Esquema multi-bot: cada mensaje lleva `bot_id + user_id` (P2); el gateway envía `bot_id` = su propio número. Ventana temporal 24h (sweep automático) + truncado a 15 msgs / ~2000 tokens al armar el contexto. `/limpiar` llama a `/reset-memory` (borra SOLO el chat del bot indicado). Testear con `BRAIN_MEMORY_DB` (env) apuntando a un .db temporal.
- `brain/.env` (gitignored, sin `.example`): `GROQ_API_KEY`, `OPENROUTER_API_KEY`, `GEMINI_API_KEY`. Sin key, la cascada se salta ese proveedor.
- Estado por contacto: `estado` (`neutro`/`permitido`/`ignorado`/`handoff`) + `globalMode` (`allowed_all`/`ignored_all`) en `settings_db.json` (`*` en `/i` `/p` cambia el modo global). **Default de deploy fresco (sin `settings_db.json`): `ignored_all` — nadie habla con el bot hasta que el admin lo permita.** Lo persistido siempre manda. Cubierto en `tests/db.test.js`.
- `settings_db.json` NO está versionado (gitignored por privacidad; contiene números de teléfono). Hay plantilla `settings_db.json.example`; los archivos legacy `allowed_numbers.json`/`ignored_numbers.json` fueron eliminados (R3, no se referenciaban).
- Comandos admin solo en self-chat (mensaje a ti mismo); texto normal ahí = asistente IA. `/` de clientes = bloqueado (seguridad).
- **Help de comandos (patrón obligatorio):** `COMMAND_USAGE` (mapa por comando canónico) + helpers `usageOf(cmd)` y `syntaxError(cmd, detalle)`. Cualquier error de sintaxis/validación DEBE responder con el help del comando en cuestión (`syntaxError`). Los targets de comandos de listas validan con `isValidTargetId()` (`*` o 7+ dígitos).
- `contacts_db.json` se limpia de basura en cada arranque (`cleanContactsDB()`).
- **Bio legada con 422:** registros viejos de `contacts_db.json` pueden tener `bio` como OBJETO `{status,setAt}` (de `sock.fetchStatus` antiguo), lo que rompe el brain con `422 Input should be a valid string`. Sanitizada en `cleanContactsDB()` (D), en `extractUserMetadata` (solo strings) y en los upserts (solo strings). `fetchStatus` devuelve un ARRAY `[{status,setAt,id}]` — tomar `[0].status`.
- **Seguridad (F2):** el brain escucha SOLO en `127.0.0.1` (`BRAIN_HOST` para override) y, si `BRAIN_API_KEY` está en `brain/.env`, TODA ruta (menos `/` health) exige header `X-API-Key` → 401. El gateway la lee sola de `brain/.env` (`getBrainApiKey()`), no hace falta configurarla en otro lado. Sin key en `.env` = modo legacy sin auth.
- **Rate limits (F2):** brain 10 llamadas/min por `user_id` en `/chat` → 429 (env `BRAIN_RATE_LIMIT_PER_MIN` / `BRAIN_RATE_LIMIT_ENABLED=0`); gateway 20 comandos admin/min (ignora el resto con aviso).
- **Markdown injection (F2):** nombres de contacto (savedName/pushName/query) se interpolaron crudos en mensajes markdown; usar SIEMPRE `sanitizeMarkdown()` (quita `* _ ` ~` y saltos de línea) antes de incrustar texto de usuario en `commandHandler.js`.
- **Baileys 7 rc14 — `downloadMediaMessage(msg, type, options, ctx)`:** el `ctx` (4º arg) lleva `reuploadRequest` (FUNCIÓN, no booleano) y `logger` (logger real). El reupload real requiere store de mensajes (no lo tenemos): `reuploadRequest: async (m) => m` reintenta con el mismo mensaje y deja llegar el error real al admin.
- Serialización por chat (B1): `chatInFlight` (Set en `messageHandler.js`) impide 2 llamadas de IA simultáneas por cliente; los mensajes que llegan durante una llamada se acumulan en el buffer y se reprograman al terminar. Los buffers huérfanos se descartan a los 15 min (B2).
- **Reconexión (F1):** al cerrarse una conexión, el gateway espera con backoff (2s→60s) antes de reconectar; NUNCA reconecta en loop inmediato. Si el socket se cae mientras responde una IA, el cliente queda en espera hasta la reconexión. **Anti-loop sin sesión (F6-P4):** `decideReconnect()` en `pipeline.js` decide si reconectar tras un cierre (lógica PURA, testeable): `loggedOut` → NO (sesión revocada); sin `creds.json` en `auth_info_baileys/` → NO (nada que reconectar: el QR/pairing lo dispara el admin desde el panel — botón "Lanzar gateway" `/api/restart` o `/api/pairing` con `needsRestart` — o `npm run reset`); con sesión → backoff normal. El loop de QR sin sesión martillea a WhatsApp (riesgo de baneo), por eso el panel se detiene a esperar.
- **Logs rotados:** `logs/` de gateway y brain están en `.gitignore`; borrarlos es seguro. El brain usa `logging` de Python — `print()` directo NO llega a `brain.log` (usar `safe_log` o `make_logger`).
- Verificar cambios: `npm run check` (gateway) + ruff/pytest (brain) antes de arrancar manualmente.
