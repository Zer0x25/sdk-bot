# F8.3 — Runbook de operación y recuperación

Este runbook separa las operaciones disponibles de las que todavía requieren una
herramienta. No usar producción como fixture ni reemplazar un archivo activo con
un snapshot antiguo.

## F8.3a — Backup completo y límite de restauración

### Estado que se respalda

| Ubicación | Contenido | Tratamiento |
| --- | --- | --- |
| Volumen `sdk-bot-production-state` | Sesión Baileys, JSON de contactos/settings/campañas, cola, memoria del Brain y `conversations.db` con sus sidecars SQLite | Copia completa sensible; incluir el volumen entero |
| Volúmenes `sdk-bot-production-gateway-logs` y `sdk-bot-production-brain-logs` | Logs rotados | No incluir en el backup de datos; conservarlos según la política de incidentes |
| `brain/profiles/` y archivos `.env` | Perfiles versionados y secretos | Recuperar perfiles desde el commit/tag desplegado y secretos desde el gestor aprobado; no meter secretos en el tar de datos |
| Volumen STT | Caché de modelos | Regenerable; no se necesita para recuperar mensajes |

La política de producto fija snapshots diarios durante siete días. No hay una
tarea programada ni una ruta externa de backups configurada por Compose en este
checkout. `archive.backup(path)` hace una copia SQLite con `VACUUM INTO` desde el
worker, pero no es un comando operativo expuesto ni cubre el resto del volumen.
Hasta automatizar y ensayar una ruta externa, el procedimiento siguiente captura
el volumen completo con los escritores detenidos.

### Captura offline

Usar un directorio del host fuera del repositorio y del volumen Docker, con
acceso restringido. Esta copia local no sustituye una réplica en otro destino.
El archivo incluye credenciales de WhatsApp, así que tratar el destino como
secreto. Descargar la imagen auxiliar antes de detener los servicios y ejecutar
el contenedor usando su digest inmutable.

```bash
set -euo pipefail
BACKUP_DIR="$HOME/backups/sdk-bot"
BACKUP_HELPER_TAG=alpine:latest
install -d -m 700 "$BACKUP_DIR"
docker pull "$BACKUP_HELPER_TAG"
BACKUP_HELPER="$(docker image inspect --format '{{index .RepoDigests 0}}' "$BACKUP_HELPER_TAG")"
case "$BACKUP_HELPER" in *@sha256:*) ;; *) exit 1 ;; esac
BACKUP_NAME="sdk-bot-state-$(date -u +%Y%m%dT%H%M%SZ)"
test ! -e "$BACKUP_DIR/$BACKUP_NAME.tar.gz"
test ! -e "$BACKUP_DIR/$BACKUP_NAME.sha256"
git rev-parse HEAD
docker compose -f deploy/docker/compose.yml images --digests

resume_stack() {
  local status=$?
  trap - EXIT
  if ! docker compose -f deploy/docker/compose.yml up -d; then
    printf '%s\n' 'ERROR: no se pudo reiniciar Compose automáticamente.' >&2
    exit 1
  fi
  exit "$status"
}
trap resume_stack EXIT
docker compose -f deploy/docker/compose.yml stop --timeout 120 panel gateway brain
docker compose -f deploy/docker/compose.yml ps --all
read -r -p '¿Panel, Gateway y Brain aparecen Exited (0)? [yes/no] ' STOPPED_OK
test "$STOPPED_OK" = yes

docker run --rm --network none \
  --mount type=volume,source=sdk-bot-production-state,target=/source,readonly \
  --mount "type=bind,source=$BACKUP_DIR,target=/backup" \
  --env BACKUP_NAME="$BACKUP_NAME" \
  "$BACKUP_HELPER" sh -ec '
    umask 077
    test ! -e "/backup/$BACKUP_NAME.tar.gz"
    test ! -e "/backup/$BACKUP_NAME.sha256"
    tar -C /source -czf "/backup/.$BACKUP_NAME.tar.gz.partial" .
    mv "/backup/.$BACKUP_NAME.tar.gz.partial" "/backup/$BACKUP_NAME.tar.gz"
    cd /backup
    sha256sum "$BACKUP_NAME.tar.gz" > ".$BACKUP_NAME.sha256.partial"
    mv ".$BACKUP_NAME.sha256.partial" "$BACKUP_NAME.sha256"
    chmod 0600 "/backup/$BACKUP_NAME.tar.gz" "/backup/$BACKUP_NAME.sha256"
  '

(cd "$BACKUP_DIR" && sha256sum -c "$BACKUP_NAME.sha256")
tar -tzf "$BACKUP_DIR/$BACKUP_NAME.tar.gz" >/dev/null
docker compose -f deploy/docker/compose.yml up -d
trap - EXIT
docker compose -f deploy/docker/compose.yml ps
```

Abortar la copia si algún escritor no se detuvo limpiamente: antes de ejecutarla,
confirmar que panel, Gateway y Brain estén `Exited (0)` en `ps --all`. No comprimir
un volumen mientras Gateway o Brain estén activos. Confirmar el checksum y
que se pueda listar el tar antes de considerar que el backup quedó capturado.
Conservar los siete snapshots diarios más recientes, eliminar los anteriores solo
después de que la nueva copia supere ambas comprobaciones y replicarla en un destino
controlado fuera del host de producción.
El runbook no configura cifrado ni el destino externo; deben ser provistos por
la plataforma de almacenamiento del operador.

### Ensayo de restauración

El worker del Gateway admite `{ restore: true }` para una copia SQLite offline:
vuelve a aplicar la retención, limpia la línea de eventos anterior y rota
`dataEpoch` antes de estar listo. El entrypoint de producción no expone un
comando de restauración, no restaura los otros archivos de estado ni reconcilia
los datos escritos después de un snapshot. Por eso, este checkout no permite
promover un snapshot antiguo sobre `sdk-bot-production-state` como recuperación
de producción.

Para un ensayo de recuperación, verificar el checksum, extraer a un volumen
Docker nuevo y aislado, y validar la copia sin conectar allí el Compose activo.
Nunca extraer sobre el volumen de producción ni usar `docker compose down -v`
para recuperar. F8.4 añade un ensayo representativo y una verificación offline
que bloquea la DB candidata si la fuente disponible avanzó o el ledger de envíos
cambió. La verificación no copia volúmenes ni reconcilia datos nuevos sobre un
snapshot antiguo. Hasta contar con la fuente detenida y un backup que pase la
puerta, conservar el volumen actual y mantener pausadas la automatización y las
salidas durante la evaluación del incidente. Si se pierde la DB activa, informar
la fecha del backup y la brecha entre esa copia y la pérdida. El RPO de hasta
24 h está especificado, pero no queda garantizado mientras no exista el job diario
y la réplica externa; no afirmar que el historial está completo ni repetir un
envío incierto.

Para materializar una copia aislada, conservar `$RESTORE_VOLUME` con un nombre
único del incidente y no añadirlo al Compose de producción. En esta terminal,
definir `BACKUP_DIR`, `BACKUP_NAME` y el digest `BACKUP_HELPER` del bloque anterior.
`GATEWAY_IMAGE` debe ser la imagen registrada para ese backup o una versión con
compatibilidad de restauración verificada explícitamente:

```bash
set -euo pipefail
RESTORE_VOLUME="sdk-bot-recovery-$(date -u +%Y%m%dT%H%M%SZ)"
test -f "$BACKUP_DIR/$BACKUP_NAME.tar.gz"
test -f "$BACKUP_DIR/$BACKUP_NAME.sha256"
(cd "$BACKUP_DIR" && sha256sum -c "$BACKUP_NAME.sha256")
if docker volume inspect "$RESTORE_VOLUME" >/dev/null 2>&1; then
  printf '%s\n' 'El volumen de ensayo ya existe; elegir otro nombre.' >&2
  exit 1
fi
docker volume create "$RESTORE_VOLUME"
docker run --rm --network none \
  --mount "type=volume,source=$RESTORE_VOLUME,target=/target" \
  --mount "type=bind,source=$BACKUP_DIR,target=/backup,readonly" \
  --env BACKUP_NAME="$BACKUP_NAME" \
  "$BACKUP_HELPER" sh -ec 'tar -xzf "/backup/$BACKUP_NAME.tar.gz" -C /target'

: "${GATEWAY_IMAGE:?Definir la imagen compatible registrada para el backup}"
docker image inspect "$GATEWAY_IMAGE" >/dev/null
docker run --rm --network none \
  --mount "type=volume,source=$RESTORE_VOLUME,target=/var/lib/sdk-bot" \
  --entrypoint node \
  --env SDK_CONVERSATIONS_DB_PATH=/var/lib/sdk-bot/conversations.db \
  "$GATEWAY_IMAGE" -e '
    const { createArchive } = require("./services/conversations");
    (async () => {
      const archive = createArchive({ path: "/var/lib/sdk-bot/conversations.db", restore: true });
      try {
        const ready = await archive.ready;
        const d = await archive.diagnostics();
        if (d.integrity !== "ok" || d.foreignKeys !== 0) throw new Error("ARCHIVE_CHECK_FAILED");
        process.stdout.write(JSON.stringify({ schemaVersion: ready.schemaVersion,
          dataEpoch: d.dataEpoch, seq: d.seq, messages: d.messages, integrity: d.integrity }) + "\n");
      } finally { await archive.close(); }
    })().catch(() => { process.stderr.write("ARCHIVE_RESTORE_STAGE_FAILED\n"); process.exitCode = 1; });
  '
```

Esto valida solo el volumen aislado y ejecuta la ruta explícita de restauración
del worker en su base SQLite. No reconcilia el delta posterior al snapshot ni
autoriza la promoción. La puerta F8.4 comprueba la paridad del archivo SQLite con
una fuente actual detenida; no comprueba el resto del volumen ni resuelve una
pérdida física sin fuente. Conservar el volumen para revisión y no promoverlo
automáticamente.

## F8.3b — Retención, purga y exportación

### Retención ejecutada por Gateway

Gateway inicia la purga antes de admitir los canales y luego intenta repetirla
cada 24 horas. Cada llamada procesa como máximo 500 filas por categoría y cede
el event loop entre lotes. Un error en la purga inicial impide completar el
arranque; un error en la tarea diaria queda en el log con una señal genérica.

| Dato | Regla efectiva | Efecto |
| --- | --- | --- |
| Cuerpos de mensaje | `ingested_at` estrictamente anterior a 90 días | Borra el cuerpo; la hora original del proveedor no extiende el plazo |
| Eventos | `created_at` estrictamente anterior a 7 días; además, se conservan como máximo 50.000 secuencias recientes | Un cursor de eventos vencido requiere resincronización |
| Huellas de deduplicación | `ingested_at` estrictamente anterior a 180 días | Antes de vencer, una redelivery no recrea un cuerpo purgado; después vence esa garantía |

La purga no borra cuentas, identidades ni estado de control conversacional. El
SQL pertenece al worker único del archivo. Esta política tampoco purga contactos,
settings, campañas, cola, memoria del Brain, sesión de canal ni logs; esos datos
no heredan automáticamente estos plazos. No ejecutar `DELETE` manual, no abrir
otra conexión escribible y no usar el backup como exportación selectiva.

### Exportación y purga por solicitud

El API autenticado de conversación ofrece páginas de lectura acotadas, pero no
hay una operación dedicada que genere una exportación vinculada al actor, auditada
y temporal por una hora según `SPEC-OPERATIVA-V1.md`. La importación/exportación
de perfiles Markdown es una operación distinta. No extraer mensajes directamente
de SQLite ni adjuntar backups completos a solicitudes de usuario.

Tampoco hay un endpoint de purga por conversación/actor. La operación `purge`
existe solo en el servicio interno y el trabajo global de retención la invoca;
no está expuesta como control administrativo autenticado.

Una solicitud de borrado inmediato tampoco se satisface esperando a la tarea
diaria: requiere una operación explícita, auditada y con invalidación de contexto.
Por ahora solo está disponible la purga global por retención. Las copias de
backup pueden conservar contenido después de la purga operativa: eliminarlas al
vencer su ventana de siete días y conservar la fecha del último snapshot verificado
para calcular la exposición residual.

Volver a una revisión de código anterior no autoriza restaurar un snapshot de
datos anterior. Si las escrituras continúan, conservar los datos actuales y
volver solo a código compatible con su schema y autoridad de control. Ver
[`SPEC-OPERATIVA-V1.md`](SPEC-OPERATIVA-V1.md) para las puertas de
migración/corte. La minimización de métricas y logs se documenta en F8.3d más
abajo.

## F8.3c — Rollback de código y corte de control

### Rollback de código sin rollback de datos

Antes de actualizar, registrar commit, digest de cada imagen, versión del schema
SQLite, autoridad del control, `dataEpoch`, secuencia y fecha/checksum del backup
verificado. En una reversión de código, conservar el mismo volumen de estado y
usar solo una imagen revisada como compatible con ese schema y autoridad. No
restaurar el backup como parte del rollback de código: mensajes, control, outbox y
ledger siguen avanzando mientras el runtime está activo. Si el código anterior
rechaza el schema o la autoridad actual, mantener el servicio detenido y usar una
versión compatible; no reemplazar datos para hacerla arrancar.

En producción Compose, detener `panel`, `gateway` y `brain` antes de reconstruir
o cambiar la imagen. Mantener `sdk-bot-production-state` montado. Después de
iniciar la versión compatible, confirmar health de Brain/Gateway/Panel, integridad
del archivo, autoridad SQLite vigente y que no haya envíos inciertos convertidos
en `queued`. `docker compose down -v` no es un mecanismo de rollback.

### Interrupción de la migración de control F5.3

Estos pasos aplican solo a una migración de control cuyo estado aún mantiene
`controlAuthority.mode=legacy`. Requieren el `migrationId` guardado en el informe
y Gateway apagado. Para reanudar, también se exige que las fuentes JSON/perfiles
sigan idénticas a las verificadas. Ejecutar desde la raíz del repo. En Compose,
el comando one-shot monta el mismo volumen y los perfiles; no levanta canales ni
dependencias:

```bash
read -r -p 'migrationId del informe: ' MIGRATION_ID
test -n "$MIGRATION_ID"
docker compose -f deploy/docker/compose.yml stop --timeout 120 panel gateway brain
docker compose -f deploy/docker/compose.yml run --rm --no-deps \
  --volume ./brain/profiles:/app/brain/profiles:ro \
  --env SDK_BRAIN_PROFILES_DIR=/app/brain/profiles \
  gateway \
  npm run conversations:control-import -- --resume-cutover --migration-id "$MIGRATION_ID"
```

`--resume-cutover` termina un corte que ya fue aprobado y vuelve a verificar que
las fuentes sigan iguales. Si el plan no debe activarse y la autoridad sigue
`legacy`, usar el rollback por lotes en lugar de reanudar; este conserva intactas
las fuentes JSON y revierte solo los controles aplicados por esa migración:

```bash
docker compose -f deploy/docker/compose.yml run --rm --no-deps \
  --volume ./brain/profiles:/app/brain/profiles:ro \
  --env SDK_BRAIN_PROFILES_DIR=/app/brain/profiles \
  gateway \
  npm run conversations:control-import -- --rollback --migration-id "$MIGRATION_ID"
```

Revisar la salida antes de levantar servicios. `status=cutover` significa que
SQLite ya es autoridad; `status=rolled_back` significa que se deshicieron solo las
entradas de control aplicadas por esa migración, con versiones monotónicas. En
ambos casos, el volumen se conserva. Si aparece `CONTROL_AUTHORITY_ALREADY_SWITCHED`,
`IMPORT_ROLLBACK_CONFLICT`, fuente cambiada o cualquier otro bloqueo, dejar Gateway
detenido y resolver con la versión/operación compatible. El `--rollback` de F5.3
no cambia SQLite de vuelta a JSON ni revierte mensajes, envíos o datos posteriores.
Solo cuando la salida confirme `cutover` o `rolled_back` se pueden levantar de
nuevo los servicios con `docker compose -f deploy/docker/compose.yml up -d`.

## F8.3d — Minimización de datos en métricas y logs

### Logs nuevos

Gateway y Brain registran eventos operativos, cantidades y etiquetas de error.
Los logs de atención no incluyen cuerpo/transcripción de mensajes, respuestas de
IA, nombres, teléfonos, JID/LID, chat ID de Telegram, identificadores de
generación ni destinatarios de campañas. Los errores se reducen a un código
acotado, estado HTTP o clase nativa conocida; los mensajes, detalles y stacks de
excepciones no se escriben en los logs de aplicación. El panel tampoco imprime
objetos de error de Telegram en la consola del navegador.

Uvicorn de Brain arranca con `access_log=False`: `/history` recibe `user_id` en la
query string, que de otro modo quedaría en la línea de acceso aunque el handler
no lo registrara. Esta opción suprime los access logs de todas las rutas de Brain;
los eventos de aplicación siguen registrándose.

### Métricas y panel

`GET /status` expone `bot.adminLinked` como booleano en lugar del número/LID del
administrador. Los motivos de desconexión se limitan a códigos conocidos; el
estado de captura WhatsApp conserva `status` y hora, con su código saneado. Los
errores recientes de Brain usan la misma etiqueta acotada. El resto del estado
expone contadores agregados, timestamps operativos y uso de recursos, sin
identidades directas ni contenido de conversación. El dashboard y la pestaña
WhatsApp muestran vínculo/sesión activa sin revelar el número.

### Límite de los logs existentes

El cambio afecta entradas nuevas y no reescribe archivos históricos. Una
instalación conserva sus logs previos hasta rotación normal (Gateway y Brain
rotan a 5 MiB con tres archivos); esos archivos pueden incluir los campos que la
versión anterior registraba. La rotación no sustituye una política de borrado
anticipado. El reset limpio elimina los logs según su inventario, pero también
borra el resto del estado de runtime y no es un control selectivo de retención.

Verificación de esta unidad: `cd apps/gateway && npm run check` pasa lint,
typecheck, 38 pruebas del panel, una prueba de integración del build y 330 pruebas
del Gateway; `cd apps/brain &&
../../brain/venv/bin/ruff check . && ../../brain/venv/bin/python -m pytest tests/ -q`
pasa 30 pruebas. Las pruebas nuevas inyectan valores centinela en una entrada de
cola, en errores y en `/status`/`/chat`, y confirman que no aparecen en logs o
métricas mientras que el contenido funcional sigue procesándose. Se usaron solo
archivos y DB temporales; no se conectaron canales ni proveedores.

### F8.4 — Ensayo aislado y puerta de frescura de restore

```bash
cd apps/gateway
SDK_CONVERSATIONS_DB_PATH=/ruta/absoluta/activa.db \
SDK_GATEWAY_LOCK_PATH=/ruta/absoluta/gateway/.gateway.lock \
npm run conversations:restore-check -- --snapshot /ruta/absoluta/copia.db
```

Compara offline y en solo lectura la DB activa configurada por
`SDK_CONVERSATIONS_DB_PATH` con el candidato. Gateway debe estar detenido y ambas
DB deben estar quiescentes, sin WAL/SHM/journal. El código 0 permite continuar
con la revisión; el código 2 indica bloqueo. La puerta permite continuar solo
si coinciden schema, epoch/secuencia, autoridad de control y la huella del ledger
completo de envíos; exige integridad/FK correctas y bloquea cualquier intent sin
resolver (`intent`, `sending` o `delivery_unknown`). Sale con código 2 y códigos
de bloqueo acotados ante una diferencia. No imprime filas, identidades ni la
huella, y nunca restaura, copia o promueve un volumen.

La comprobación debe ejecutarse después de detener el gateway y antes de
restaurar o promover. Un resultado `promotionAllowed: true` afirma que el archivo
de conversaciones del candidato coincide con la fuente detenida en ese momento;
no valida los otros archivos/volúmenes del despliegue ni sustituye el backup
offline coherente del volumen completo. Si la fuente actual no existe, la
paridad no se puede demostrar: mantener el restore aislado, describir el
intervalo posterior al backup que no cubre y decidir la recuperación por separado.

El ensayo F8.4 migra un fixture desde contactos/settings y activa la autoridad
SQLite; registra una respuesta humana aceptada antes del backup; luego añade un
aviso aceptado sin evento, un intento sin resolver y una nueva entrada con otra
respuesta humana. La puerta bloquea el aviso aunque la secuencia de eventos no
cambie, bloquea el intento pendiente y bloquea el snapshot antiguo por la entrada
y el envío nuevos. Ese snapshot se restaura solo en una DB temporal, rota el
epoch, conserva la respuesta previa y no contiene el delta; la fuente original
mantiene el aviso y ambas respuestas. Un backup nuevo de la fuente pasa la
puerta. Esto verifica el control de archivo SQLite, no una promoción productiva
ni la recuperación del resto del volumen.

Verificación: `cd apps/gateway && node --test tests/conversationRecovery.test.js`
(1/1) y `npm run check` (lint, typecheck, panel: 38 pruebas + 1 prueba de
integración/build, Gateway: 331/331); el ensayo cubre corte F5, salida humana
aceptada, ledger-only, envío sin resolver, rechazo del snapshot obsoleto, restore
aislado y aceptación de backup actual. Se usaron solo archivos temporales; no se
conectaron canales ni proveedores.

### Límite del rollback de datos

La restauración de un backup antiguo sobre el archivo activo después de nuevas
escrituras no es un rollback soportado. No elimina/reemplaza el volumen para
volver a un punto temporal: eso descartaría mensajes recibidos, salidas humanas,
control y resultados inciertos posteriores. F8.4 bloquea una copia de archivo
obsoleta cuando la fuente sigue disponible y su delta se puede comparar. En una
pérdida física sin fuente actual, restaurar solo en un destino aislado y reportar
el intervalo que el backup no cubre antes de decidir una recuperación.
