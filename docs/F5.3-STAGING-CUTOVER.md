# F5.3 — Staging, delta y corte recuperable

## Esquema y staging

SQLite migra de v5 a v6 sin reemplazar el archivo ni modificar `dataEpoch`,
`seq` o los controles que ya existían. Añade perfil/revisión por conversación,
política global, estado de autoridad y tablas de migrationId, ejecuciones, entradas
y snapshots. El modo de autoridad inicial sigue `legacy`.

`npm run conversations:control-import` es de solo lectura por defecto. Con
`--apply` calcula el mismo informe F5.2 y guarda las entradas por lotes de hasta
250. Un `migrationId` por defecto deriva de `dataEpoch`; se puede fijar con
`--migration-id`. Repetir una ejecución con las mismas fuentes continúa la misma
ejecución; cualquier cambio de fuente o del snapshot SQLite produce una nueva
ejecución bajo ese migrationId. Los SHA-256 del archivo, inventario de perfiles,
epoch y secuencia vinculan el plan a su snapshot. La CLI vuelve a comprobar las
fuentes antes de verificar y antes de cambiar la autoridad.

El staging no escribe columnas de control activas. La verificación exige que todas
las entradas estén guardadas, que los recuentos cuadren y que no queden bloqueos.
Una eliminación respecto de una ejecución previa o un cambio de conversación
destino se pone en cuarentena. La revisión puede aceptarse de forma explícita con
`--accept-source-removals` o `--accept-identity-changes`; la decisión queda en el
informe persistido. Los conflictos restantes, perfiles ausentes y estados
desconocidos conservan el corte bloqueado.

## Corte y recuperación

`--cutover` aplica solo un plan verificado, en transacciones de hasta 100 entradas.
Cada conversación guarda su estado anterior antes de la escritura. Cada conversación
cambiada emite `control.changed` para que los lectores invalidados recarguen. El
corte verifica estado, política global e integridad, y cambia `control_authority`
únicamente al final.
El servicio común de F5.4 debe marcarse listo antes de ese paso; si no, la CLI
devuelve `CONTROL_SERVICE_NOT_READY` y conserva el staging verificado.

Si el proceso cae durante la aplicación parcial, el gateway y el dry-run rechazan
abrir el archivo con `CONTROL_CUTOVER_RECOVERY_REQUIRED`. Tras validar que las
fuentes siguen iguales, reanudar con:

```bash
npm run conversations:control-import -- --resume-cutover --migration-id <id>
```

Para restaurar el snapshot previo mientras la autoridad aún es legacy:

```bash
npm run conversations:control-import -- --rollback --migration-id <id>
```

El rollback se procesa por lotes, verifica que cada estado sigue siendo el
aplicado por esta migración y avanza las versiones al restaurar. No permite
volver a JSON después de activar SQLite; los JSON de origen permanecen intactos
y son exportables para respaldo.

## Límites de esta unidad

No se ejecutó `--apply` contra datos de runtime. La prueba usa SQLite y JSON
temporales. La autoridad no cambia en F5.3 porque los lectores y writers del
runtime aún usan JSON; F5.4 integrará el servicio compartido y habilitará la
activación. El gateway apagado y el lock exclusivo de SQLite evitan writers
simultáneos durante staging/corte. Un cambio de fuente entre validaciones deja el
corte sin activar y requiere rollback o un nuevo dry-run.

Esta unidad no resuelve los defectos de salida duplicada BUG-050 (F5.6), ni
reconcilia automáticamente mensajes históricos anteriores a SQLite v3 (BUG-051).
No apareció un defecto adicional sin resolver para el backlog.
