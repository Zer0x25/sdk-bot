# F7.3 — Canales

Fecha: 2026-10-22. Implementación del panel React sobre el gateway actual; no
inicia ni duplica los transportes.

## Alcance

- `/inbox/channels` muestra el estado seguro de cuentas WhatsApp/Telegram mediante
  `/api/v1/accounts`. El pairing solo aparece con el grant servidor `admin:write`.
- WhatsApp reutiliza `/pairing/status`, `/qr/refresh`, `/pairing` y el SSE `/qr`.
  El estado QR/código se restaura al abrir la pantalla; el QR se cierra al salir.
  El bus mantiene la ventana de 140 s, el límite de refresh y la exclusión entre
  QR y código. Código y número solo se muestran en la vista administrativa.
- Telegram se identifica como canal administrativo. La vista no lee el token:
  consulta solo indicadores booleanos en `/telegram/settings/meta` y pide token
  y Chat ID al guardar. No llama `/telegram/test` ni simula atención de clientes.
- BUG-024 queda cerrado: con OAuth, toda ruta `/api/*` legacy y la UI antigua
  requieren `admin:write` explícito. Sesiones de solo lectura mantienen acceso a
  `/inbox/*`; el control se aplica en el panel antes del proxy y no depende de
  `X-Status-Token`.

## Verificación

- `npm run check` en la raíz: contratos generados/tipados y 17 pruebas, todas pasaron.
- En `gateway`, reinstalación con `npm ci --no-audit`; se ejecutaron el chequeo de
  versión de Baileys y el postinstall de protobufjs. `npm run check` pasó lint,
  typecheck, 21 pruebas React, build y montaje del panel, y 320 pruebas Gateway.
- Cobertura específica: el grant de solo lectura no alcanza status/QR/logs/
  command/reset ni la UI legacy; `admin:write` sí permite status/UI. Las vistas React
  prueban estados de pairing restaurados; la metadata TG no devuelve token/Chat ID.

No se conectó una cuenta de proveedor, no se emitió un QR/código real y no se envió
mensaje de Telegram. El test heredado de `/telegram/test` usa un servidor simulado.
